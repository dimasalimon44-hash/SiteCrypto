1. ОБЩЕЕ ОПИСАНИЕ ПРОЕКТА
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Сайт отображает межбиржевые спреды USDT-перпетуальных фьючерсов в режиме
реального времени. Пользователь видит разницу в цене между биржами и может
открыть длинную позицию на одной бирже и короткую — на другой (cash-and-carry
или чистый ценовой арбитраж). Дополнительно показываются ставки фандинга,
прогноз 24h фандинга и оставшееся время до следующей выплаты.

Стек технологий:
  Backend  : Python 3.10+, FastAPI, Uvicorn, aiohttp, httpx, orjson, Redis
  Frontend : HTML5, CSS3, Vanilla JS (без фреймворков)
  Реалтайм : SSE (Server-Sent Events) для push-обновлений в браузере
  Биржи    : MEXC, Bybit, BingX (REST + WebSocket)
  Безопасность: RSA-OAEP шифрование паролей при передаче, PBKDF2-SHA256 хранение
  Auth     : Bearer JWT-like токены, шифрованная БД пользователей (Fernet)
  Telegram : Бот-уведомления при привязке аккаунта

Файловая структура:
  app.py              — основной FastAPI-сервер + REST-коллектор (одно-процессный режим)
  collector.py        — отдельный процесс: только сбор данных с бирж → Redis
  ws_collector.py     — WebSocket-коллектор: подписка на WS-стримы бирж → Redis
  models.py           — dataclass MarketRow (одна строка биржа/монета)
  templates/          — Jinja2 HTML-шаблоны (dashboard.html, graph.html)
  static/js/          — dashboard.js, graph.js
  static/css/         — dashboard.css, graph.css
  assets/             — логотипы бирж, звуки уведомлений
  services/           — пустой (зарезервирован)
  scripts/            — auto_redeploy.sh, install_ngrok.sh, run_with_ngrok.sh

2. АРХИТЕКТУРА — СИЛЬНЫЕ СТОРОНЫ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[+] ТРИ РЕЖИМА РАБОТЫ — хорошо спроектировано:

    a) Однопроцессный (для разработки):
       python app.py
       — updater_loop и HTTP-сервер в одном процессе.

    b) Двухпроцессный REST-коллектор (рекомендуется для ~50 пользователей):
       python collector.py  (читает биржи → пишет в Redis)
       python app.py        (только HTTP, COLLECTOR_ONLY=1)
       — Нагрузка сбора данных полностью отделена от HTTP.

    c) WebSocket-коллектор (рекомендуется для скальпинга):
       python ws_collector.py  (WS-стримы → in-memory → Redis каждые 300 мс)
       python app.py           (только HTTP, COLLECTOR_ONLY=1)
       — Задержка обновления спредов: 50–300 мс вместо 3–10 сек.

[+] РЕАЛТАЙМ ЧЕРЕЗ SSE:
    Браузер подключается к /events один раз и получает push-обновления.
    Нет polling каждые N секунд — экономия трафика и мгновенная доставка.

[+] INITIAL DATA INJECTION:
    При первой загрузке страницы данные уже встроены в HTML через
    <script id="__initial-data__">...</script>. Нет «белого экрана» 1–2 сек.

[+] КЭШИРОВАНИЕ ИНТЕРВАЛОВ ФАНДИНГА:
    _MEXC_INTERVALS, _BYBIT_INTERVALS, _BINGX_INTERVALS — in-memory кэш.
    Данные не запрашиваются заново на каждом цикле. Redis TTL 24ч —
    выживают перезапуски сервера.

[+] GRACEFUL DEGRADATION ДЛЯ BINGX:
    Bulk-запрос → при отсутствии данных fallback на per-symbol API.
    Bid/ask отсутствуют → используется lastPrice. Хорошая отказоустойчивость.

[+] БЕЗОПАСНОСТЬ ПАРОЛЕЙ:
    RSA-OAEP шифрование при передаче (пароль никогда не идёт в открытом виде).
    PBKDF2-SHA256 хранение с солью. Секретный ключ через env var ARB_AUTH_KEY.

[+] GZip MIDDLEWARE:
    GZipMiddleware снижает трафик ответов на 70–80%.

[+] uvloop:
    Если установлен — используется автоматически (2–3× быстрее asyncio).

[+] ЛОГИРОВАНИЕ:
    RotatingFileHandler (LOG_FILE), уровень через LOG_LEVEL.
    Подавление дублей от uvicorn (propagate=False).

КРИТИЧНО (влияет на работу в продакшне)
─────────────────────────────────────────

[!] ПРОБЛЕМА: REFRESH_SEC=3 в REST-режиме — слишком агрессивно для скальпинга
    Файл: app.py, константа REFRESH_SEC = int(os.getenv("REFRESH_SEC", "3"))
    При трёх биржах и 200+ символах каждый цикл делает ~10–15 HTTP-запросов.
    С задержкой сети 300–800 мс цикл занимает 1–3 сек. Спред приходит с
    задержкой 3–10 сек — недостаточно для скальпинга.
    РЕШЕНИЕ: Использовать ws_collector.py (задержка 50–300 мс). REST-режим
    оставить только как fallback. В ЗАПУСК_ИНСТРУКЦИЯ.txt это уже описано.

[!] ПРОБЛЕМА: app.py — 2614 строк в одном файле
    Всё в одном файле: auth, биржи, SSE, конфиг, роуты, утилиты.
    При дальнейшей разработке будет сложно поддерживать.
    РЕШЕНИЕ: Разбить на модули:
      exchanges/mexc.py, exchanges/bybit.py, exchanges/bingx.py
      auth.py, sse.py, routes/api.py, routes/auth.py, config.py
    Это не срочно, но необходимо при масштабировании команды.

[!] ПРОБЛЕМА: Глобальные переменные для состояния
    _MEXC_INTERVALS, _BYBIT_INTERVALS, _BINGX_INTERVALS, _HTTP_SESSION,
    _REDIS, LIVE_ROWS, _DATA_CACHE, _SSE_QUEUE — всё глобальное.
    При переходе к multi-worker (uvicorn --workers N) каждый воркер имеет
    своё состояние. Это нормально только если Redis используется как
    единственный источник истины (COLLECTOR_ONLY=1).
    РЕКОМЕНДАЦИЯ: Явно документировать это ограничение. Убедиться что
    COLLECTOR_ONLY=1 всегда выставлен при --workers > 1.

[!] ПРОБЛЕМА: Нет rate limiting на /api/auth/login
    Эндпоинт /api/auth/login не защищён от брутфорса.
    PBKDF2 с 100 000 итерациями замедляет атаку, но не блокирует.
    РЕШЕНИЕ: Добавить slowapi (rate limiter для FastAPI) или Redis-счётчик
    неудачных попыток по IP: 5 попыток → блокировка на 60 сек.

4. ПРОИЗВОДИТЕЛЬНОСТЬ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Режим          | Задержка спреда | CPU (2vCPU) | HTTP запросов/час
  ───────────────┼─────────────────┼─────────────┼──────────────────
  REST (одно)    | 3–10 сек        | 20–35%      | ~2000
  REST (2-проц.) | 3–10 сек        | 15–25%      | ~2000
  WS-коллектор   | 50–300 мс       | 3–8%        | ~5 (bootstrap)

  Для скальпинга нужен WS-коллектор. REST-режим подходит для мониторинга
  долгосрочных арбитражных позиций (часы/дни), но не для быстрых входов.

  Bottleneck в REST-режиме:
  - BingX: до 200 символов × несколько HTTP запросов = самый медленный источник.
    Bulk-запросы (bookTicker, ticker24h, premiumIndex, fundingRate) параллельны,
    но ответы содержат 200–300 элементов и занимают 200–500 мс каждый.
  - MEXC: один bulk ticker — быстро (~150 мс).
  - Bybit: ticker + instruments-info (кэш 1ч) — ~200 мс.

  Память при 200 символах × 3 биржи:
    LIVE_ROWS: ~200 × 6 пар × ~500 байт = ~600 КБ — незначительно.
    Redis arb:snap:* ключи: ~3 JSON × 50–200 КБ = ~300–600 КБ — OK.
